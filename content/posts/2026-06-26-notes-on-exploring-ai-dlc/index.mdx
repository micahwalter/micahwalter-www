I've spent the last few months using agentic AI tools to build things. Not just asking a model to write a function, but handing it a real project and watching it work through requirements, architecture, code, and even operational tasks. Along the way I stumbled into something called the **AI-Driven Development Life Cycle**, or AI-DLC for short, and it has changed how I think about what software development even is anymore.

This post is my attempt to write down what I have been learning. It covers the vocabulary, the phases, the roles, the tooling, and how spec driven development fits into the picture. If you are trying to make sense of agents, specs, and the future of building software, maybe some of this will be useful.

## The problem with bolting AI onto the old process

For a long time, the industry has treated AI as a faster autocomplete. You get code completion in your IDE. You ask a chatbot to explain an error. You generate a unit test. Helpful, sure, but the underlying process stays the same: product managers write requirements in Confluence, engineers break work into Jira tickets, architects draw boxes in Lucidchart, developers branch off main, open pull requests, and wait for review.

That model was designed for humans doing human paced work. Meetings, sprint planning, backlog grooming, design reviews. Weeks to move from idea to shipped feature.

When you drop a capable agent into that same process, something weird happens. The agent can generate a requirements document in minutes. It can propose an architecture. It can write thousands of lines of code. But if nobody has validated what it should actually build, you end up with fast garbage. Velocity without fidelity.

The [AWS DevOps blog post on AI-DLC](https://aws.amazon.com/blogs/devops/ai-driven-development-life-cycle/) describes this tension well. AI assisted development (AI as helper) and AI autonomous development (AI builds the whole thing from a prompt) both fall short on their own. What we need is a new lifecycle where AI is a central collaborator, not a sidecar and not an oracle.

## What is AI-DLC?

AI-DLC is a methodology for building software with AI as a first class participant in every phase. The core idea is simple: **the AI creates a plan, asks clarifying questions, waits for human validation, then executes**. That loop repeats for every activity in the lifecycle.

There are two dimensions that make it work:

1. **AI powered execution with human oversight.** The agent does the heavy lifting (drafting requirements, writing code, generating tests) but defers critical decisions to humans who understand business context.
2. **Dynamic team collaboration.** Instead of everyone working in isolation on their piece, the team comes together for rapid validation. AWS calls this "Mob Elaboration" during planning and "Mob Construction" during building.

The methodology is organized into three phases:

```
INCEPTION       →  What and why (planning, requirements, architecture)
CONSTRUCTION    →  How (design, code, tests)
OPERATIONS      →  Deploy and run (infrastructure, monitoring)
```

Each phase feeds context into the next. Artifacts like requirements, design docs, and plans are stored in the project repository so work can continue across sessions. This is important. Agents forget. Files do not.

The open source rules for all of this live in the [awslabs/aidlc-workflows](https://github.com/awslabs/aidlc-workflows) repository. You can drop those rules into tools like Amazon Q Developer, Kiro, Cursor, or Claude Code and the agent will follow the workflow.

## Inception: turning intent into something buildable

The Inception phase is where business intent becomes structured, validated work. This is the phase that product people and architects care about most.

### Workspace Detection

Every AI-DLC engagement starts by figuring out what you are working with. Is this a greenfield project or a brownfield codebase? Is there existing documentation? Are there prior AI-DLC artifacts from a previous session? The agent scans the workspace and decides what comes next.

I have been running AI-DLC on this very blog (yes, the one you are reading). The agent detected a brownfield Next.js project, ran reverse engineering to document the architecture, and established a living docs folder at `aidlc-docs/` for ongoing work. That baseline means every future session starts with context instead of cold.

### Reverse Engineering (brownfield only)

When you have an existing codebase, the agent analyzes it before planning changes. It produces artifacts like business overview, architecture documentation, component inventory, API docs, and technology stack analysis. This is the agent doing what would take a new engineer weeks of reading code.

### Requirements Analysis

This is where the agent takes your request ("add a newsletter signup form" or "migrate from Lambda to containers") and turns it into structured requirements. Depth varies by complexity:

- **Minimal** for simple, clear requests
- **Standard** for normal feature work
- **Comprehensive** for high risk or ambiguous changes

The agent asks clarifying questions in a structured format (multiple choice with an "other" option) and waits for your answers before proceeding. No guessing.

### User Stories

When the work affects users or has multiple scenarios, the agent creates user stories with acceptance criteria and personas. This stage is conditional. A bug fix might skip it. A new checkout flow would not.

In the traditional world, user stories live in Jira. In AI-DLC, they live in the repo as markdown artifacts, traceable back to requirements. The product manager role shifts from writing stories in a ticket tracker to reviewing and approving stories the agent drafts.

### Workflow Planning

Before any code gets written, the agent creates an execution plan: which stages to run, in what order, at what depth. This is adaptive. A one line bug fix might go straight from requirements to code generation. A new microservice gets the full treatment with application design, unit decomposition, NFR analysis, and infrastructure design.

### Application Design and Units of Work

For larger changes, the agent identifies components, services, methods, and business rules. Then it decomposes the work into **units of work**, which replace the traditional "epic" concept. A unit might be a single deployable service or a logical module within a monolith.

AI-DLC also replaces "sprints" with **bolts**: shorter, more intense cycles measured in hours or days rather than weeks. The terminology reflects the speed change.

## Construction: from design to working code

Once Inception artifacts are validated, Construction begins. This is where engineers traditionally spend most of their time, and it is where agents are most visibly powerful.

### Per unit design stages (conditional)

For each unit of work, the agent may run additional design stages:

- **Functional Design**: Business logic, data models, business rules
- **NFR Requirements**: Performance, security, scalability needs
- **NFR Design**: Patterns for meeting those requirements
- **Infrastructure Design**: Mapping to actual cloud resources (ECS, Lambda, DynamoDB, etc.)

These stages are conditional. A CSS tweak does not need infrastructure design. A new API endpoint with auth and rate limiting does.

### Code Generation

This always runs. It has two parts:

1. **Planning**: The agent creates a detailed implementation plan with checkboxes
2. **Generation**: The agent executes the plan, writing code and tests

The plan step matters. Without it, you get undirected code dumps. With it, you get traceable implementation that maps back to requirements and design artifacts.

### Build and Test

After all units are complete, the agent generates build instructions, unit test instructions, and integration test instructions. On this blog, that means `npm run build` as the primary correctness signal since there is no test runner configured.

## Operations: where the story is still being written

The Operations phase is a placeholder in the current AI-DLC spec, but the intent is clear. The agent should eventually manage infrastructure as code, deployments, monitoring, and incident response using all the context accumulated during Inception and Construction.

I think about this as the phase where the agent stops being a developer and starts being an operator. Proposing CloudFormation changes, running deploys, setting up alarms. Always with human oversight, but doing the tedious sequencing work that eats ops time.

## Spec driven development and how it relates

If AI-DLC is the lifecycle, **spec driven development** is one way to structure the artifacts within it. Kiro, Amazon's agentic IDE, has a particularly well defined take on this.

A Kiro spec produces three files for every feature:

| File | Purpose |
|------|---------|
| `requirements.md` | User stories and acceptance criteria |
| `design.md` | Architecture, sequence diagrams, error handling |
| `tasks.md` | Discrete, trackable implementation tasks |

The workflow is three phases: Requirements, Design, Tasks. Each phase has approval gates. The agent does not skip ahead without human sign off.

Kiro also supports **bugfix specs** with a parallel structure focused on root cause analysis instead of user stories. And it has a **Quick Plan** mode for well understood features where all three artifacts generate in one pass.

The relationship to AI-DLC is straightforward. Kiro specs are the artifact format. AI-DLC is the lifecycle that tells you when to create them, what comes before and after, and how they connect to code generation and testing. You can read more in the [Kiro specs documentation](https://kiro.dev/docs/specs/).

### Specs vs vibe coding

Kiro draws a useful line:

- **Use specs** when building complex features, fixing costly bugs, collaborating with a team, or when requirements need iteration
- **Use vibe coding** when prototyping, exploring, or when you do not yet know what you want

I have been guilty of vibe coding far too often. It is fun and fast until you need to come back to the code a week later and have no idea what the agent was thinking.

## The roles: who does what in an agentic world

One thing that surprised me about AI-DLC is how clearly it maps traditional roles to new responsibilities. The roles do not disappear. They shift.

### Product Manager / Product Owner

Still owns the "what" and "why." But instead of writing PRDs in Confluence and grooming a Jira backlog, the PM reviews and approves requirements and user stories that the agent drafts. The PM answers clarifying questions. The PM validates that what the agent understood matches business intent.

The Jira backlog might still exist for tracking, but the source of truth for a given piece of work lives in the repo as markdown artifacts.

### Architect

Still owns structural decisions. Which services to create, how components communicate, what the deployment model looks like. The architect reviews application design and infrastructure design artifacts. The agent proposes, the architect approves or redirects.

In practice I have found the architect role merging with the senior engineer role. When you are a team of one with an agent, you wear both hats.

### Engineer / Developer

Still owns implementation quality. But the job shifts from typing code to reviewing code, validating plans, running builds, and making judgment calls the agent cannot make. The engineer approves code generation plans, reviews diffs, and decides when something is good enough to merge.

This is the shift the AWS blog describes as moving from routine coding to critical problem solving. I felt this acutely during my [Mastodon server upgrade with Claude](/posts/notes-on-upgrading-my-mastodon-server-in-about-an-hour-with-claude). I was not typing commands. I was approving sequences and watching for things that looked wrong.

### QA / Test Engineer

The agent generates test instructions and test code, but someone still needs to validate that the tests cover the right scenarios. In AI-DLC, this role is less about writing test cases and more about reviewing test plans and ensuring edge cases are covered.

### DevOps / SRE

Owns the Operations phase. Reviews infrastructure designs, approves deployment plans, validates monitoring and alerting. As the Operations phase matures, this role will increasingly involve reviewing agent proposed infrastructure changes rather than writing CloudFormation by hand.

## Git workflows in an agentic world

Agents need somewhere to work, and that means thinking carefully about Git.

### Branching

Every piece of agent work should happen on a branch. This blog post was written on a branch called `cursor/ai-dlc-blog-post-b0c6`. The agent creates the branch, makes commits, and opens a pull request. Main stays clean.

Branch naming conventions matter when agents are creating branches autonomously. A predictable pattern like `cursor/<description>-<id>` makes it easy to see what the agent was working on.

### Pull Requests

PRs become the primary review surface. Instead of reviewing code line by line in an IDE, you review the agent's PR: the code, the commit messages, and ideally the linked artifacts (requirements, design, tasks) that explain why the changes exist.

### Forking

Forking is less relevant for solo or small team work on a single repo, but it matters when agents work across organizational boundaries or when you want isolation between experimental agent runs and production code.

### Worktrees

This is the one I find most interesting. Git worktrees let you check out multiple branches simultaneously in separate directories. For agentic development, this means you can have one agent working on a feature in one worktree while you review its previous PR in another, without stashing or switching branches.

I have not fully adopted worktrees yet, but I can see a future where multiple agents (or multiple sessions) work in parallel worktrees on different units of work, each with its own set of AI-DLC artifacts.

### Where this leaves Jira and Confluence

I do not think Jira and Confluence go away. They serve different purposes.

**Confluence** (or Notion, or whatever your team uses) is still where high level product vision, roadmaps, and cross team communication live. AI-DLC artifacts are not a replacement for your company wiki. They are the implementation level specs that feed into code.

**Jira** (or Linear, or GitHub Issues) is still where you track work status, assign owners, and manage priorities across the team. On this blog, [GitHub Issues is the backlog](https://github.com/micahwalter/www/issues). AI-DLC docs reference issues by number but do not duplicate them.

The shift is that the detailed specs, designs, and plans move from Jira/Confluence into the repo, versioned alongside the code they describe. Traceability improves because you can follow a line from a requirement to a design decision to a line of code to a test, all in git history.

## What I have been doing with all of this

I have AI-DLC rules wired into this blog project. The agent reverse engineered the codebase and produced architecture docs, component inventories, and API documentation. It captured requirements for ongoing work and established conventions for how AI-DLC artifacts relate to GitHub Issues.

When I ask the agent to build something on this site, it follows the workflow: detect the workspace, analyze requirements, plan which stages to run, get my approval, then generate code. Every interaction gets logged in an audit trail. State persists across sessions.

It is not perfect. The Operations phase is still a placeholder. Some stages feel heavy for small changes. And I still catch myself vibe coding when I should be writing a spec first. But the direction feels right.

## The mental model that stuck with me

The pattern that keeps coming back is this:

```
Plan → Ask → Validate → Execute → Repeat
```

The AI plans. The AI asks questions. The human validates. The AI executes. Then the cycle starts again for the next stage.

That is the opposite of "prompt and pray," where you describe what you want and hope the model figures it out. It is also the opposite of traditional waterfall, where humans plan for weeks before anyone writes code.

It is something in between. Fast enough that you can iterate in hours. Structured enough that you build the right thing. Human enough that critical decisions still belong to people who understand the business.

If you want to go deeper, start with the [AI-DLC workflows repository](https://github.com/awslabs/aidlc-workflows), read the [AWS blog post](https://aws.amazon.com/blogs/devops/ai-driven-development-life-cycle/), and try the [Kiro specs workflow](https://kiro.dev/docs/specs/) on a real feature. The best way to understand this stuff is to run it on something you actually care about.
